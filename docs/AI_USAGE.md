## 2. Example of Rejected / Corrected AI Output (Microarchitectural Integrity)

### The Issue: Cache Invalidation Pathology (Cache Stampede Risk)
During the scaffolding of `packages/rag_core/src/rag_core/cache/invalidation.py`, the AI assistant proposed a naive cache invalidation observer that executed a global `FLUSHDB` / `invalidate_all()` on any catalog update event:

```python
# REJECTED AI OUTPUT:
class CacheInvalidator(CatalogObserver):
    async def on_catalog_update(self, update: CatalogUpdate) -> None:
        # Naive approach generated by AI: Purged the ENTIRE cache on every single price update
        await self._exact.invalidate_all()
        await self._semantic.invalidate_all()
```

### Why It Was Rejected:
In a production ecommerce scenario with high-frequency catalog updates (e.g. weekend flash sales or stock changes), flushing the entire Redis cache creates a catastrophic cache stampede, forcing subsequent chat requests to re-execute expensive dense embeddings, pgvector similarity searches, and cross-encoder rerankers, degrading p95 latency by >10x.

### The Corrected Implementation:
We rejected the AI suggestion and re-architected `ExactCache` and `SemanticCache` with a Product-to-Query Inverted Index (`rag:exact:product:{product_id}` set mapping). Invalidation now surgically purges only the specific cache keys referencing the modified product IDs, preserving unaffected entries and maintaining steady-state cache hit rates:

```python
# CORRECTED PRODUCTION ARCHITECTURE:
async def invalidate_by_product_id(self, product_id: str) -> int:
    product_set_key = f"{self.PRODUCT_MAP_PREFIX}{product_id}"
    keys = await self._client.smembers(product_set_key)
    if not keys:
        return 0
    pipe = self._client.pipeline()
    pipe.delete(*keys)
    pipe.delete(product_set_key)
    await pipe.execute()
    return len(keys)
```
